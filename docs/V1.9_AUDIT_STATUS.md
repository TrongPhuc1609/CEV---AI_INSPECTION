This status records the current boundary between software verification and physical validation for the V1.9 physical vision trial.

## Audit findings fixed in this revision

### 1. Incomplete replay scoring could be accepted silently
Previously, `evaluate_real_trial.py` evaluated only the prediction rows supplied to it. A partial predictions file could therefore produce a plausible metric without covering the full frozen manifest.

**Fix:** evaluation now requires an exact one-to-one sample-ID set between manifest and predictions. Missing, unknown, or duplicate prediction IDs fail the evaluation.

### 2. Duplicate manifest samples could distort results
A duplicated `sample_id` in the manifest could represent one physical sample more than once.

**Fix:** `run_real_trial_batch.py` now rejects duplicate sample IDs and invalid empty sample/image identifiers.

### 3. Defect-class performance was documented but not emitted
The validation plan requires performance by defect type, but the evaluator previously emitted only aggregate metrics.

**Fix:** `evaluation.json` and `evaluation.html` now include metrics grouped by `defect_type`.

## Remaining physical gaps — not software bugs

The following cannot be closed by code alone:

1. A real labelled image dataset is still required. The repository reserves `data/physical_trial/images/`, but the directory currently contains only its README/contract rather than a committed trial dataset.
2. Ground Truth must be human-verified and frozen before acceptance scoring.
3. The current machine-vision recipe is a measurement boundary, not a commissioned component/grease classifier.
4. Camera characterization must be performed with the actual camera/lighting/product setup.
5. Motion/frame correlation must be measured on the actual conveyor.
6. PLC remains simulated; physical reject acknowledgement and actuation are not yet verified.
7. Product-specific acceptance thresholds must be supplied from the real product/process requirement rather than invented in software.

## Required next physical test sequence

### Phase R — Real-image replay

Collect and label GOOD/NG images for every supported defect class plus borderline/acquisition edge cases. Freeze the manifest, then run:

```text
python tools/run_real_trial_batch.py data/physical_trial/manifest.jsonl
python tools/evaluate_real_trial.py data/physical_trial/manifest.jsonl --predictions data/physical_trial/results/predictions.jsonl
```

Archive:
- manifest;
- evaluation.json;
- evaluation.html;
- exact commit SHA;
- exact Rule.cmd/config revision;
- dataset checksum/location.

### Phase C — Live camera

Use `CAPTURE_CAMERA.bat`. Record resolution, exposure, focus/blur, saturation, lighting, board position and ROI stability. Link captured frames to labelled samples before using them as inspection evidence.

### Phase M — Motion

After R and C gates pass, measure trigger-to-frame latency, product/frame correlation, timeout, stale-frame, duplicate and skipped-product behavior on the real conveyor.

### Phase P — PLC/reject

After R/C/M gates pass, verify GOOD/no reject, NG/reject+acknowledgement, PLC unavailable, timeout, duplicate/late acknowledgement and physical reject position/timing.

## Non-claims

A green CI run or successful ZIP artifact does **not** establish production inspection accuracy, real camera stability, conveyor timing, or physical PLC reject success. Those claims require the corresponding R/C/M/P evidence.
