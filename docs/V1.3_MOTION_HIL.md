# V1.3 Motion, Timing and HIL

## Purpose

V1.3 protects inspection validity when the product is moving. A frame is only useful if the product velocity is inside the configured operating envelope and the PASS/NG decision reaches the reject point before the physical reject window closes.

## Runtime safety

1. Trigger and frame are correlated before Vision/Rule execution.
2. Product velocity is read from trigger metadata when available; otherwise the configured nominal velocity is used for simulation/HIL.
3. Velocity outside `MOTION.min_velocity..max_velocity` blocks the inspection and sends NG.
4. `camera_to_reject_distance / |velocity|` defines the available reject window.
5. The measured trigger-to-PLC cycle time is compared with that window. If exceeded, the PLC command is forced to NG with `REJECT_WINDOW_EXCEEDED`.
6. Timing samples are retained by `TimingCollector` and can be persisted by the existing audit path.

## HIL scenarios

- nominal slow movement: 0.25 units/s -> inspection allowed
- below minimum: 0.05 units/s -> blocked
- above maximum: 0.75 units/s -> blocked
- reject window sufficient -> PLC decision allowed
- reject window exceeded -> forced NG
- stale/mismatched frame -> blocked before Vision

## Commissioning acceptance

The HIL suite is a software gate only. Production acceptance still requires real encoder/trigger measurements, real camera acquisition, real PLC timing and a physical reject actuator test on the target conveyor.
